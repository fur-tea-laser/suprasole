* **PtyProcess charter:** suprasole's sole owner of the PTY process from fork to reap — a state machine aligned with the kernel's process lifecycle (issue §4B).
  * **States:** `Alive{pidfd, Pid}` → (`Zombie_Withheld{pidfd, Pid}` →) `Zombie{pidfd, Pid, Termination}` → `Reaped{Termination}`, or → `SystemError{error}`.
    * **Handle and PID** exist only in the states in which the kernel still holds the process, so the PID cannot have been recycled.
    * **Termination** exists only once the process has terminated: `Exited{ExitCode}` or `Signaled{Signal, Status_CoreDump}`.
    * **Final states resolve the exit outcome themselves:** `Reaped` through its `Termination` (`Exited{0}` → `Success`, other codes → `Failure`, `Signaled` → `Killed`); `SystemError` → `SystemError_Process`.
  * **Concurrency:** `Mutex` guards `State_state`; `RunWorker` is its only writer, and writes each transition inline under the Mutex. `Channel_FinalState` closes strictly after the final state is written and the pidfd closed — the channel is the wake-up, `State_state` is the truth.
  * **`Prepare__Command_PtyProcess(api)`:** turns the client's request (`_PrepareApi__Command_PtyProcess_{Path_ShellBinary, Path_Directory, Environment}`) into the `_Command_PtyProcess_` that `Spawn_PtyProcess` passes to `execve` exactly.
    * **Order:** `check__NUL_PtyCommand` first, then `resolve__Path_ShellBinary`, then the struct. `Argv` is `[Path_ShellBinary]`, the name as sent; the environment is passed exactly as sent, duplicates included.
    * **It can fail:** a NUL byte (`fork/exec` / `chdir` / the environment message), or an unknown bare name (`*exec.Error` from `exec.LookPath`).
  * **`Spawn_PtyProcess(path_PtyExec, command_PtyProcess, fileDescriptor_slave__Pty)`:** starts the PTY program through the spawn helper `suprasole-pty-exec` (code in `source/PtyExec/`, companion doc `PtyExec.md`). The launcher supplies its path with `-Path_PtyExec`; `main` passes it through `WorkspaceController` to the orchestrator, the same route as `OptionConfig_PtyProxy__default__`.
    * **Why a helper:**
      * Go's `ForkExec` vforks. The forking thread cannot be preempted until the child execs, so a child that blocks before `execve` stalls every stop-the-world and freezes the server. Blocking happens on `chdir` into, or `execve` of, a path on a hung network filesystem, and the client chooses both paths.
      * `ForkExec` also reports a bare errno from the child, so a bad `Dir` read as `fork/exec <shell>: ENOENT`.
      * The helper moves every client-controlled step out of the vfork window. `ForkExec` now only execs a small local binary. The helper — a separate process with no Go runtime — does the rest and reports the exact step that failed.
    * **`ForkExec` of the helper:**
      * `argv` = `[path_PtyExec, Path_Directory, Path_Executable, Argv…]`. `command_PtyProcess` is a `_Command_PtyProcess_`, not an `exec.Cmd`: its four fields reach `execve` exactly, with no implicit lookup, deduplication or inheritance. `Argv` includes `argv[0]`.
      * `envp` = `Environment`, exactly as given, duplicates included. The helper has no runtime, so variables like `GODEBUG` configure nothing.
      * `Files` = the slave three times (fds 0–2), plus the report pipe's write end (fd 3).
      * `Sys` = `PidFD` only. No `Setsid`, `Setctty` or `Dir`: the helper does those itself.
      * **Descriptor duplication, not data copying:** fork duplicates the whole descriptor table. `execve` drops every close-on-exec descriptor (the master, the original slave, the pidfd, the report pipe's read end), leaving the `dup3` copies on 0–3. The helper marks fd 3 close-on-exec first, so the shell's own `execve` drops it.
      * **`PidFD` → `CLONE_PIDFD`:** the process and its handle come from the same syscall. `execve` keeps the PID, so the pidfd names the helper and then the shell.
    * **The report pipe decides the outcome.** After `ForkExec`, the parent closes its copy of the write end and reads 16 bytes through the netpoller (`io.ReadFull`): a parked goroutine, no thread held.
      * EOF with nothing read: the shell's `execve` succeeded, and closed fd 3.
      * Exactly 16 bytes: `{step, errno}`, two little-endian `uint64`s. The helper failed at that step and exits with 127; `Spawn_PtyProcess` starts its collection (below).
    * **Errors name the real cause:**
      * `ForkExec` failure (helper missing, resource limits) → `*os.PathError{Op: "fork/exec", Path: path_PtyExec}`. Go has already collected the failed child and closed the pidfd.
      * A `CHDIR` report → `*os.PathError{Op: "chdir", Path: Path_Directory}`, the op `os.StartProcess` uses for its own `Dir` check.
      * An `EXECVE` report → `*os.PathError{Op: "fork/exec", Path: Path_Executable}`, as exec reported it before.
      * **Requires NUL-free strings, as a precondition.** The orchestrator guarantees it: `Prepare__Command_PtyProcess`, the first call in `Spawn_PtyProxy`, runs `check__NUL_PtyCommand` on the client's request before resolving the shell name, so no PTY is opened for an invalid request.
        * The check names the field: shell path → `fork/exec <path>` / `EINVAL`; directory → `chdir <dir>` / `EINVAL`; an environment entry → the message `exec.Cmd.Start` gave ("exec: environment variable contains NUL").
        * It runs before the lookup because `exec.LookPath` would report a bare name containing NUL as "executable file not found in $PATH", hiding the real reason.
        * A NUL that still reached `Spawn_PtyProcess` fails loudly, not silently: `ForkExec` refuses it with `EINVAL`, reported as `fork/exec <helper>`.
    * **Blocks its goroutine until the helper execs or fails.** If the helper hangs in `chdir` or `execve` on a hung filesystem, `Spawn_PtyProcess` waits indefinitely. That costs one parked goroutine (the caller's), never a thread, and the server keeps running. No timeout policy exists yet.
    * **A helper killed before `execve`** (by someone else's `SIGKILL`) also closes fd 3 without a report. The spawn succeeds, and the worker then observes the process killed. That is a true outcome: the process existed.
    * **A pidfd the worker could never watch is abandoned at spawn time.** After `ForkExec`: set `O_NONBLOCK`, wrap with `NewFile`, check `SetReadDeadline(time.Time{})` — Go documents that only pollable files support it, so it fails exactly when the pidfd cannot be parked in the netpoller. Its one real cause is the netpoller refusing to register it (`epoll_ctl` `ENOMEM`, or `ENOSPC` from `fs.epoll.max_user_watches`). The spawn fails with that error. `Spawn_PtyProcess` abandons the process inline: it kills the group through the pidfd (`sendSignal_Pidfd`, result ignored), then starts `reapAbandoned__PtyProcess_Pidfd`, a goroutine that collects it with `waitid(WEXITED|WNOHANG)`, sleeping `INTERVAL_REAP_ABANDONED__PtyProcess` (1 s) between empty answers, then closes the file. That constant is its own, not the re-peek's: it waits for a killed process to finish dying, and since nobody waits on this reaper, a long interval costs nothing and keeps wake-ups rare if the process cannot die.
      * **It owns the `*os.File`, not the raw number:** once `NewFile` owns the descriptor, closing the bare number would let the file's finalizer later close a reused one. Every access goes through `Control`; a `Control` failure (nil or closing file — impossible, since this goroutine alone owns and closes it) falls into the final `else`. The kill's `errno` is ignored on purpose: whether or not it lands (e.g. `EPERM` after a credential change), the reaper collects the process whenever it terminates.
      * **Two live branches:** nothing yet (sleep, normally once) and a termination — `CLD_EXITED`, `CLD_KILLED` or `CLD_DUMPED` — (done, exactly once).
      * **Everything else falls into the final `else`, which lists it and panics.** None has a branch in the source; why each cannot occur:
        * **A `Control` failure** — impossible: this goroutine alone owns and closes the file.
        * **`ECHILD`** — a real kernel case (the child was collected by someone else), unreachable while exclusive reaping holds (issue §5B.2).
        * **A trap report (`CLD_TRAPPED`)** — the man pages allow one, but since Linux 5.19 `SIGKILL`'s fatal wake clears `JOBCTL_TRACED` inside `kill()`, `wait` reports a ptrace stop only while it is set, and a dying task enters no new stop (verified at v6.9, issue §6-AN). This rests on suprasole making no ptrace request: only a tracer's own requests set `JOBCTL_PTRACE_FROZEN`, the one state the fatal wake leaves alone.
        * **`CLD_STOPPED` / `CLD_CONTINUED`** — not selected without `WSTOPPED` / `WCONTINUED`; a traced child's stops arrive as `CLD_TRAPPED`.
        * **`EINTR`** — impossible: the call passes `WNOHANG`, and `wait(2)` raises `EINTR` only without it.
      * **Never holds an OS thread:** a blocking `waitid` would pin one for as long as a `D`-state or debugger-held process survives, and the netpoller refused the pidfd, so it cannot be waited on there. A sleeping goroutine holds only a runtime timer.
    * **Setting `O_NONBLOCK` cannot fail, so `wrap__Pidfd` asserts it:** its final `else` lists `error_setNonblock__Pidfd__maybe != nil` and panics. On a valid pidfd private to `Spawn_PtyProcess`, `F_GETFL` returns `O_RDWR`, `setfl` has no failure clause that a lone `O_NONBLOCK` change can reach (pidfs has no `check_flags` / `fasync`), and every in-tree `file_fcntl` security hook passes. Full derivation from Go 1.27.1 and kernel v6.9 source: issue §3B. It rests on issue §5A.2: no seccomp errno filter or BPF-LSM program injects failures.
    * **`launchPtyExec__Command_PtyProcess` is named for its mechanism:** it launches the PtyExec helper, carrying the command. It is not a plain fork/exec of the command; the helper execs the command itself.
    * **It keeps `syscall.ForkExec`'s own promise:** it returns once the PTY program has exec'd, or with the precise error — never a half-failed child. `ForkExec` itself waits on a close-on-exec pipe for its child's verdict; this function extends that wait to the helper's `execve` of the shell. Every resource is created and handled inside it, so no raw descriptor or pipe end crosses a function boundary. It calls:
      * `wrap__Pidfd`: `O_NONBLOCK` (asserted) and `NewFile`, so the pidfd has an owner the moment it exists.
      * `await__Report_PtyExec`: reads the report through the netpoller and decodes it.
        * `ABSENT` = EOF, no report. This is the exact mechanism, true both after a successful `execve` and after a helper killed before it.
        * `REPORTED` = a whole `{step, errno}` record.
        * It asserts the impossible rest: a short report (16 bytes is below `PIPE_BUF`, so the helper's single `write` is atomic) and any other read error.
      * `resolve__PathError_PtyExec`: report → `chdir <Path_Directory>` or `fork/exec <Path_Executable>`. It asserts that `ARGUMENTS`, `SETSID`, `TIOCSCTTY` and `RT_SIGPROCMASK` are unreachable when `Spawn_PtyProcess` runs the helper (`PtyExec.md`).
    * **Its returned pidfd states whether a process exists:**
      * fork failed → `(0, nil, error)`: no process; Go has already collected the child and closed its pidfd.
      * the helper reported a failure → `(0, pidfd, error)`: the helper is exiting and must be collected.
      * exec succeeded → `(pid, pidfd, nil)`.
    * **`Spawn_PtyProcess` decides, and starts every goroutine itself** (the orchestrator starts goroutines, never the helpers it calls). It checks pollability first: `SetReadDeadline` on a nil `*os.File` returns `os.ErrInvalid` without touching anything, so computing it before the chain is safe in every case.
      * error + no pidfd → return the error.
      * error + pidfd → `go reapAbandoned__PtyProcess_Pidfd` (no kill: the helper is already exiting), return the error.
      * no error + pidfd + not pollable → abandon, `netpoll` error.
      * no error + pidfd + pollable → `Alive`.
      * The final `else` lists the impossible rest and panics: no error and no pidfd.
    * **No pidfd after a successful fork** happens only on a kernel that ignores `CLONE_PIDFD` (before 5.2) — below the floor the launcher guarantees, so it is not handled. A full descriptor table does not produce it: the kernel fails the whole fork (`EMFILE`).
    * **`O_NONBLOCK` before `os.NewFile`,** so the netpoller registers the pidfd.
    * **Does not start `RunWorker`:** the orchestrator does — `Spawn_PtyProxy`, right after this returns. A process that terminates before the worker starts is not missed: the zombie waits for its parent, and `RawConn.Read` peeks before it ever waits.
  * **`Signal(signalNumber_PtyProcess, flags__PIDFD_SEND_SIGNAL)`:** each state answers for itself, because only some states hold a pidfd. The caller holds the Mutex around the call, in its own body: `Mutex.Lock()` → `State_state.Signal(…)` → `Mutex.Unlock()`. `_PtyProcess_` has no method that locks internally, so no lock is taken out of the caller's sight and none can nest.
    * **`Alive` / `Zombie_Withheld` / `Zombie`:** `pidfd_send_signal` through the pidfd. The worker closes the pidfd only after writing a final state under the same Mutex, so a send never meets a closed handle.
    * **`Reaped`:** `os.ErrProcessDone`. **`SystemError`:** its own error. Neither holds a handle, so there is no syscall to make; after the reap the kernel would have answered `ESRCH` anyway, but after a poller failure the process may still be alive.
    * **A successful send is not evidence the process is alive:** the kernel accepts and ignores signals to a zombie, and a group signal still reaches live members.
    * **The scope is the kernel's own flag, passed straight through:** `PIDFD_SIGNAL_THREAD_GROUP` (the PTY process) or `PIDFD_SIGNAL_PROCESS_GROUP` (its group), both Linux 6.9 — no enum of our own to translate. `PIDFD_SIGNAL_THREAD_GROUP` is stated explicitly rather than flags `0`, which makes the kernel infer the same scope from the pidfd's type. `PIDFD_SIGNAL_PROCESS_GROUP` is defined for a group leader, and `Setsid` makes the PTY process one for life. The kernel rejects unknown bits, or two scope flags at once, with `EINVAL`.
    * **One function, `sendSignal_Pidfd(fileDescriptor_pidfd__PtyProcess, signalNumber_PtyProcess, flags__PIDFD_SEND_SIGNAL)`,** sends through the pidfd's `*os.File`: `SyscallConn` → `Control` → the raw `pidfd_send_signal` inside the callback, with the `Control` assertion written once. Its only callers are the three pidfd-holding states' `Signal` and `Spawn_PtyProcess`'s abandon branch (which ignores the result on purpose); the worker never signals.
    * **A `Control` failure is asserted, not handled:** `Control` fails only for a nil or closing file, and each kind of caller guarantees the file cannot be closing: the states' callers hold the Mutex while the worker closes the pidfd only after writing a final state under it; `Spawn_PtyProcess`'s abandon branch owns the file exclusively until the reaper closes it, and starts that reaper only after the kill returns. A failure can only mean a caller broke that guarantee (most likely: calling a state's `Signal` without the Mutex). Ignoring it would report "sent" when the callback never ran; instead the final `else` lists it and panics.
    * **The `errno` branch is live:** `EPERM` when the PTY process has changed credentials (e.g. the PTY program is `su`, which sets its real UID to another user). `ESRCH` cannot occur in a non-final state — the process is unreaped, and an unreaped zombie leader still belongs to its group — and `EINVAL` is excluded by valid arguments.
  * **Constants:** `pidfd_send_signal` is syscall 424 in the post-5.1 unified table (identical on amd64 / arm64); `P_PIDFD`, `POLLIN` and the `CLD_*` codes come from `waitid(2)` / `poll(2)`. `_SigInfo_Waitid_` is the 64-bit `siginfo_t` layout for `SIGCHLD`.
  * **`Observe_Unresponsive()`:** the teardown's observation, which each state answers for itself under the caller's Mutex (code in `PtyTeardown.go`, companion doc `PtyTeardown.md`).
    * **`Alive` / `Zombie_Withheld`:** `UNRESPONSIVE`, plus the `/proc/<Pid>` report (state letter + `TracerPid`). The PID is still ours, because the worker reaps only inside the Mutex.
    * **`Zombie` / `Reaped` / `SystemError`:** `TERMINATED`, with no report — `Channel_FinalState` is about to close, and the final state will be the report.
    * It replaced phase 2's interim `waitid(P_PID)` probe (`ProbeStatus_Unresponsive`), which was blind to `D` and to debugger-held processes.
