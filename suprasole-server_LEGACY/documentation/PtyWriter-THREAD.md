* **Unified Event-Driven Worker Runloop & Ingress Coordination (for { select { ... } })**:
  * **Colocated Same-Depth Cancellation (Deadlock & Leak Immunity)**:
    * **Same-Depth Structural Requirement**: Placing case <-this.WorkerContext.Done(): directly alongside case inputOrder_next := <-this.QueueChannel_InputOrder: at the exact same select depth is the only configuration that simultaneously guarantees zero-CPU idle sleep and unparking upon child process termination.
    * **Failure of Top-Level Check with Nested Blocking Read (Goroutine Leak)**: Structuring cancellation as an outer select (case <-this.WorkerContext.Done(): with a top-level default:) containing a nested select with solely case inputOrder_next := <-this.QueueChannel_InputOrder: (and no nested default:) causes a fatal leak; if the child process terminates while the queue is empty, the worker parks unconditionally on the inner nested select and never returns to the outer loop to re-evaluate WorkerContext.Done().
    * **Failure of Top-Level Check with Nested Polling (CPU Busy-Spin)**: Adding a nested default: alongside case inputOrder_next := <-this.QueueChannel_InputOrder: in that inner select transforms the runloop into an unthrottled non-blocking poll, burning 100% of a CPU core spinning across empty channel checks during human typing pauses.
  * **Pseudo-Random Selection & The Close-Before-Write Race**:
    * **Simultaneous-Ready Arbitration**: When WorkerCancel() fires while input orders remain in QueueChannel_InputOrder, Go's runtime arbitrates pseudo-randomly between the two ready cases.
    * **Deferred Exit Execution**: If an input order is selected over Done(), RunWorker() does not terminate immediately; it dispatches inputOrder_next.WriteInput() against a master file descriptor that may already be closing or closed concurrently by process teardown (__executeTeardown_Exited / FileDescriptor_Master__PtyDevice.Close()), which safely resolves to nil (kernel discard) or os.ErrClosed.
    * **Guaranteed Bounded Termination**: Because upstream ingress (HandleWriteInput_Ingress) immediately drops new submissions once WorkerContext.Done() closes, no further orders can enter the queue, guaranteeing the worker exits cleanly on subsequent loop iterations without requiring a sync.WaitGroup join barrier.
  * **Strict FIFO Transmission**: Serializes all terminal stdin inputs through the channel, guaranteeing interactive keystrokes and escape sequences arrive at the PTY device in exact chronological order.

* **Kernel Write Buffer Saturation & Upstream Backpressure Propagation**:
  * **External Upstream Ingress Strategy (Non-Blocking Transport Shield)**: Upstream WebSocket ingestion (HandleWriteInput_Ingress) enqueues keystrokes into QueueChannel_InputOrder using a non-blocking channel send (select with default). When a stalled child process causes the channel buffer to saturate, excess keystrokes are dropped immediately rather than blocking the upstream PTY WebSocket ingress thread.
  * **Internal PtyWriter Strategy (Dedicated Concurrency & Kernel Isolation)**: Linux pseudo-terminal slave input queues enforce finite kernel quotas (canonical 4 KB line-discipline buffer and 64 KB pipe buffer). When a slave child process (bash, vim, less) pauses reading from stdin (/dev/pts/N), the kernel buffer saturates and subsequent write(2) system calls against the master descriptor block in kernel space. Isolating writes to an independent, dedicated per-PTY PtyWriter.RunWorker() goroutine confines kernel backpressure to the specific stalled session, ensuring write blocking never contends locks or stalls scheduling on sibling PTYs or shared threads.

* **Master PTY Descriptor System Call & Error Suppression (_, _ = this.FileDescriptor_Master__PtyDevice.Write)**:
  * **Byte-Count Discard & Partial-Write Safety**:
    * **Counterintuitive Byte Discard**: In standard Unix/POSIX systems programming, discarding the returned byte count on a write system call is a notorious antipattern that risks silently dropping data during partial writes (such as large multi-kilobyte clipboard pastes).
    * **Go Runtime Internal Write Loop**: In Go, os.File.Write does not expose raw partial write(2) returns to user-space; it wraps an internal runtime loop (poll.FD.Write) that automatically retries on syscall.EINTR and loops repeatedly until the entire slice is transmitted (n == len(this.InputData_PtyDevice)) or an error occurs.
    * **All-or-Nothing Transmission Guarantee**: Because Go's runtime guarantees complete transmission before returning a nil error, maintaining a manual user-space partial-write loop in PtyWriter is completely redundant.
    * **Irrelevance of Partial Bytes on Failure**: If Write fails partway through with an error, the terminal session is already terminating or closed, making tracking how many partial bytes reached the dead buffer irrelevant.
  * **Teardown Error Alignment & Reader Exit Arbitration**:
    * **Closing and Closed Descriptor Write Semantics**: Executing Write() during or after process teardown resolves safely across two distinct layers: if the master descriptor remains open in Go but the child process has exited, the raw kernel write(2) system call succeeds with nil error while the kernel discards unread slave input; once FileDescriptor_Master__PtyDevice.Close() executes, Go's runtime descriptor wrapper (poll.FD) detects the closed state via internal reference counting and immediately returns os.ErrClosed without issuing a system call (preventing EBADF).
    * **Strict Error Symmetry with PtyReader (Absence of Asymmetric Write Errors)**: Writing to the PTY master device produces no unique or asymmetric write error classes (such as broken-pipe errors); every failure condition encountered by this.FileDescriptor_Master__PtyDevice.Write() (specifically os.ErrClosed) directly mirrors an error condition handled by PtyReader.
    * **Liveness Asymmetry (Why Exit Arbitration Belongs to Reader)**: PtyReader's continuous blocking read(2) unparks instantly on child exit, whereas PtyWriter calls write(2) only opportunistically on keystrokes and cannot detect termination during idle periods.
    * **Split-Brain Telemetry & cmd.Wait() Concurrency Race**: If PtyWriter attempted to handle os.ErrClosed as an exit trigger, it would race with PtyReader to execute process teardown (calling ptyCommand.Wait() concurrently, which fails with "exec: Wait was already called") and dispatch conflicting duplicate exit orders to LifecycleCoordinator_WorkspacePty.
