* **Dual Core Responsibilities of PtyDispatcher (Output Pacing & Process Teardown Orchestration)**:
  * **Paced Egress & Batch Coalescing (Stdout/Stderr Streaming)**: PtyDispatcher decouples kernel reading from network transmission and terminal emulation updates. Rather than forwarding raw kernel reads directly to downstream consumers—which would overwhelm WebSocket clients and incur excessive lock contention under heavy burst output—PtyDispatcher regulates output flow using a hybrid immediate-and-paced strategy:
    * **Interactive Fast-Path Dispatch**: When idle, the first incoming byte chunk bypasses the staging buffer and flushes immediately, preserving single-keystroke interactivity and zero perceived typing latency.
    * **Framerate-Capped Batch Coalescing**: Subsequent bursts arriving during the active pacing window are coalesced into a 96 KB staging buffer and flushed at an approximate 60 Hz cadence (~16.6 ms target, subject to runtime scheduler and OS timer granularity), throttling network packet emission and batching memory grid updates in PtyTerminal under PtyProxy.Mutex.
  * **Initial Exit Teardown & Granular Lifecycle Classification (Process Termination Orchestration)**: PtyDispatcher serves as the authoritative single point of exit handling for the pseudo-terminal session, executing immediate kernel resource reclamation before delegating lifecycle coordination:
    * **Kernel PTY Resource Reclamation**: Upon receiving an exit order, PtyDispatcher stops the pacing timer, synchronously flushes any residual staged bytes, closes the master descriptor (FileDescriptor_Master__PtyDevice.Close()), and reaps the terminated child process (PtyCommand.Wait()) to capture OS process exit status and prevent zombie processes.
    * **Granular Exit Classification & Coordinator Order Submission**: Rather than surfacing a generic termination event, PtyDispatcher inspects the ingress ExitSignal and raw POSIX WaitStatus, classifying termination into one of five granular outcomes (Closed, Success, Failure with exit code, Killed by signal, or SystemError) and submitting an atomic ExitPty order to QueueChannel_WorkspaceOrder for centralized lifecycle reconciliation in LifecycleCoordinator_WorkspacePty.

* **Paced Output Flushing Strategy & State Machine Architecture**:
  * **Output Pacing Semantics & State Machine Dynamics**:
    * **Architectural Problem & Polarity Harmonization (Interactive Latency vs. Throughput Throttling)**: Terminal byte streams exhibit radical behavioral polarity: single-keystroke interactive typing demands immediate sub-millisecond echo latency, whereas heavy stdout bursts (such as compilation logs, package installations, or streaming dumps) produce hundreds of fragmented read chunks per second. Transmitting raw reads unbuffered overwhelms WebSocket transport and incurs heavy mutex contention across server and client parsers, while pure periodic batching introduces unacceptable typing lag. PtyDispatcher harmonizes this behavioral conflict through a bimodal immediate-and-batched pacing state machine, providing 0 ms leading-edge latency for human typing while enforcing a framerate-capped batching cadence during sustained output bursts.
    * **Bimodal State Invariants (Interactive Latency vs. Active Burst Coalescing)**: The state machine operates as an asymmetric two-phase automaton:
      * **Interactive Fast-Path (IDLE Phase)**: Optimizes exclusively for echo latency. The initial read chunk bypasses the staging buffer entirely and flushes synchronously to PtyTerminal and connected WebSocket clients with 0 ms added delay. Arming Timer_FlushPacing post-flush guarantees that subsequent burst data receives its full timeout duration undiminished.
      * **Active Burst Coalescing (PACING Phase)**: Optimizes exclusively for batching throughput. Subsequent read chunks arriving while the temporal window is active are consolidated into the 96 KB staging buffer, decoupling upstream kernel reads from downstream rendering and network transmission.
    * **Periodic Cadence Throttle vs. Sliding Debounce Invariance**: Pacing enforces a strict periodic cadence rather than a sliding debounce. In contrast to input debouncers that reset deadlines on incoming events, Pacing allows countdowns to run uninterrupted to their trailing edge. Resetting deadlines on incoming data would create an unbounded sliding delay that postpones terminal emission indefinitely during high-throughput stdout streaming. Enforcing fixed periodic windows guarantees bounded, predictable batch flushes every ~Timeout__Timer_FlushPacing interval regardless of kernel read frequency.
    * **Trailing-Edge Idle Recovery & Fast-Path Priming**: Output burst cessation is resolved on the trailing edge of the pacing window. Allowing the timer to expire on an empty buffer transitions the dispatcher back to idle sleep without re-arming. This guarantees zero CPU overhead during terminal silence while automatically re-priming the zero-delay fast-path for the user's next interactive keystroke.
  * **Pacing Mechanics**:
    * **Channel Draining Invariants & Clean Re-Arming**: PtyDispatcher restricts Timer_FlushPacing.Reset strictly to initial idle-to-pacing transitions or trailing-edge execution points where the tick has already been consumed by the select statement. By architectural design, there are no realistic scenarios where an unprocessed tick can sit in Timer_FlushPacing.C when Reset is invoked.
    * **Uniform Select Arbitration Robustness & Non-Flush Execution Bounds**: When both QueueChannel__Order_PtyDispatcher and Timer_FlushPacing.C are simultaneously ready, Go select resolves readiness via pseudo-random uniform selection. Even during sustained bursts where multiple queued data orders win arbitration consecutively before the timer tick is handled, the select loop remains robust. Because the non-flush path is strictly limited to in-memory slice appending and freelist return (~300 to 400 nanoseconds), multi-order arbitration streaks take only single-digit microseconds. This microsecond delay is negligible compared to operating system timer jitter and allows contemporaneous data orders to coalesce into the pending flush batch without meaningfully starving the timer.

* **Virtual Terminal Emulator State Synchronization (This.PtyTerminal.Write(UnflushedSlice_StagingBuffer__PtyDispatcher))**:
  * **Unconditional Consumption Across Client Visibility Modes**: PtyTerminal.Write executes unconditionally before evaluating This.Mode_state. Regardless of whether a client is actively receiving live WebSocket packets (LIVE_RUNNING), temporarily disconnected or backgrounded (PRE_SNAPSHOT__RUNNING), or awaiting snapshot transition acknowledgment (POST_SNAPSHOT__RUNNING), the virtual terminal emulator continuously digests output. This decouples child process terminal progression from client network presence, ensuring backgrounded tabs accumulate accurate scrollback history and remain ready for instant snapshot serialization without state drift.
  * **Thread Safety & Mutual Exclusion under Mutex (This.Mutex)**: The xterm-go emulator grid is not thread-safe and contains mutable multi-line structures shared with other concurrent subsystems, specifically PtyResizer (which calls PtyTerminal.Resize on viewport dimension changes) and snapshot serialization routines (which traverse screen buffers). Executing PtyTerminal.Write strictly within the This.Mutex critical section guarantees mutual exclusion, preventing concurrent memory corruption, visual tearing, or race conditions during simultaneous resizing and output ingestion.
  * **Shared Pacing Strategy (Terminal Emulation & Output Egress Parity)**: PtyDispatcher routes both sinks through a single, shared flushing strategy for internal terminal emulation and external network transmission. Binding both operations to the same coalesced slice (UnflushedSlice_StagingBuffer__PtyDispatcher) inside HandleBlockingFlush guarantees that server-side terminal state mutation and live client egress advance in strict temporal lockstep across identical chunk boundaries. Consolidating both consumers behind one shared staging buffer simplifies memory management, while extending the 60 Hz pacing cadence to emulator writes amortizes This.Mutex contention: the lock is acquired once per pacing interval or once on leading-edge interactive strokes, streaming dense multi-kilobyte batches into the VTE parser in a single atomic call while preserving responsiveness for concurrent operations like PtyResizer and snapshot generation. Confining PtyTerminal.Write strictly to this singular flush minimizes order processing in the worker loop and ensures emulator execution never delays timer tick processing.
  * **Synchronous Processing Complexity & Execution Bounds (In-Memory CPU Duration under Mutex)**: PtyTerminal.Write is a purely synchronous, in-memory CPU operation executing within the This.Mutex critical section, performing zero kernel syscalls, disk operations, or network I/O. Execution complexity scales strictly linearly O(N) with byte volume across sequence parsing and in-memory grid updates. For standard high-throughput output bursts (such as compilation logs or continuous stdout streams), digesting a fully saturated 96 KB staging buffer completes in approximately 1.3 ms to 2.0 ms—consuming less than 12% of the 16.6 ms pacing frame budget.
    * **Pathological Degenerate Worst-Case Ceiling**: Pathological streams packed with dense full-screen clears (CSI 2J) represent the worst-case CPU ceiling: repeatedly sweeping the entire terminal grid can degrade synchronous execution into the low hundreds of milliseconds (~200 ms), temporarily starving concurrent PtyResizer adjustments and snapshot serialization. Even under such adversarial bursts, mutex hold times remain strictly bounded by finite in-memory computation rather than unbounded kernel or network wait states.

* **Process Termination Orchestration & Granular Exit Classification**:
  * **FIFO Exit Serialization & Lossless Trailing Flush Invariant**: The exit signal order shares the identical FIFO channel queue as data orders, meaning all preceding kernel-read originated pty bytes are guaranteed to be processed before teardown initiates. Residual staged bytes are first flushed before proceeding to exit teardown and exit classification to ensure zero trailing byte loss.
  * **Process Teardown Mechanics (__executeTeardown_Exited)**: Teardown guarantees that all operating system resources are synchronously reclaimed—closing the master descriptor and reaping the child process—before exit classification initiates:
    * **Master PTY Descriptor Teardown (_ = FileDescriptor_Master__PtyDevice.Close())**: Reclaiming the master descriptor before child process reaping enforces terminal clean-up across kernel and runtime boundaries:
      * **Upstream Coordinator Invalidation & Teardown Cascade**: When initiated upstream by LifecycleCoordinator during cancellation, master closure unparks PtyReader with os.ErrClosed, propagating an exit order to PtyDispatcher where downstream Close executes as a safe, redundant no-op.
      * **Conditional Kernel Resource Reclamation & Child-Process Deadlock Prevention**: If not closed earlier, master closure frees OS terminal resources and delivers hangup signals to the foreground process group, unblocking stdin-suspended children so process wait never deadlocks.
      * **Go Runtime Poller Deregistration & Descriptor Invalidation**: Go deregisters the descriptor from runtime polling to eliminate stale events, and invalidates the handle to safely reject late operations like trailing PtyWriter inputs.
      * **Teardown Error Indifference & Blank Assignment (_ =)**: Because teardown is reactive and the session is already terminating, the return error from Close is inconsequential. Discarding the return value absorbs all nominal, redundant, and benign closure results, ensuring execution unconditionally proceeds to process reaping.
    * **Child Process Reaping & Process Exit Status Capture (_ = PtyCommand.Wait())**: Reaping the child process finalizes process lifecycle cleanup across operating system, runtime, and process state layers:
      * **OS Zombie Reaping & Process Table Reclamation**: Reaping the terminated child releases its entry from the operating system process table, preventing zombie processes from accumulating and exhausting system PID quotas.
      * **Runtime Process State Synchronization Barrier**: Wait acts as a mandatory barrier that populates PtyCommand.ProcessState with exit codes and signal status, ensuring subsequent classification routines never read uninitialized exit state.
      * **Exit Error Suppression & Blank Assignment (_ =)**: Discarding Wait's return value bypasses Go's generic ExitError on non-zero or signaled exits, enabling downstream classification to extract exact exit codes and signals directly from ProcessState.
  * **ExitSignal Interpretation & Granular Classification Mechanics**: Accurately classifying session termination requires an orchestrated interpretation dance that distinguishes self-contained descriptor signals from child process hangups requiring deep exit status drilling:
    * **Initial Descriptor Signal Discrimination (Self-Contained vs. Ambiguous Signals)**: PtyDispatcher evaluates the raw ExitSignal order to determine whether classification is immediately complete or requires child process status inspection:
      * **Administrative Invalidation (Closed - Self-Contained)**: os.ErrClosed immediately classifies intentional server-side shutdown; because termination was initiated by the host, the child process state is superseded and requires no exit status drilling.
      * **System I/O Faults (SystemError - Self-Contained)**: Unrecognized kernel errors directly classify unexpected master descriptor failures, packaging the raw OS error without needing child status inspection.
      * **Canonical Process Hangup (syscall.EIO - Ambiguous & Polymorphic)**: Linux PTY semantics dictate that child process termination unblocks master reads with syscall.EIO (unwrapped via errors.Is). Unlike Closed or SystemError, syscall.EIO is inherently polymorphic and carries three valid, mutually exclusive interpretations (clean exit, application failure, or signal death), meaning it cannot be resolved from descriptor signals alone.
    * **Prerequisite Teardown Barrier & Process State Population**: Because syscall.EIO cannot discriminate child exit states on its own, execution must satisfy a strict sequence prerequisite before drilling further:
      * **Teardown Synchronization Barrier**: The dispatcher invokes __executeTeardown_Exited to close the master descriptor and synchronously reap the child via PtyCommand.Wait().
      * **Process State Population Invariant**: Process reaping acts as the mandatory synchronization barrier that populates PtyCommand.ProcessState; attempting to evaluate child status prior to this prerequisite would inspect uninitialized memory.
    * **POSIX Status Drilling & Tri-State EIO Classification**: Once child reaping satisfies the process state prerequisite, HandleDispatchExited_Eio inspects syscall.WaitStatus to drill into the three valid interpretations of syscall.EIO:
      * **Clean Execution (Success)**: waitStatus.Exited() with exit code 0 resolves syscall.EIO as normal process completion.
      * **Application Failure (Failure)**: waitStatus.Exited() with a non-zero code resolves syscall.EIO as an application error, preserving the exit code for client reporting.
      * **Signal Termination (Killed)**: waitStatus.Signaled() resolves syscall.EIO as abnormal termination, extracting the terminating signal number.
