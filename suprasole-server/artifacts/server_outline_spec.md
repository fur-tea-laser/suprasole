# Architectural Specification: State-Synchronized Headless VTE Server (`suprasole-server`)

This specification defines the complete, state-synchronized architecture, layered component interaction, and resync execution model for `suprasole-server`.

The server provides multi-terminal process management and real-time state synchronization for web clients running `xterm.js`. It pairs Operating System pseudo-terminal (PTY) process isolation via `creack/pty` with an in-memory headless Virtual Terminal Emulator (VTE) state machine engine via `gitpod-io/xterm-go` and single-writer FIFO WebSocket egress serialization.

---

## 1. Executive Architectural Principles

* **Decoupled Layered Architecture**: Strict separation of concerns divides the system into three distinct tiers: the Network Gateway (transport & protocol envelopes), the Workspace Controller (lifecycle & resync orchestration), and the PTY Process (pure OS process & VTE state machine).
* **Zero-Kernel-Blocking Reader Loop**: Operating System kernel PTY reads are **never paused, throttled, or delayed** under any circumstances. Kernel PTY buffers ($64\text{ KB}$) remain continuously drained, completely eliminating process deadlocks and kernel buffer saturation.
* **Passive-Tap Dual-Path Reader**: Incoming stdout streams from the kernel read loop are processed concurrently along two paths. Bytes update the in-memory headless terminal state engine (`xterm-go`) while conditionally streaming to workspace callbacks based on the process's operational mode.
* **Connection-Loss State Safeguard**: Upon WebSocket disconnection, the server immediately transitions `PtyProcess` into `ModePreSnapshot` under lock ($< 5\text{ \mu s}$) and unbinds network egress callbacks. All stdout produced while disconnected is absorbed live into `xterm-go` memory for the eventual reconnect snapshot.
* **Strict Zero-Syscall Mutex Invariant**: Operating System kernel system calls (`read(master_fd)`, `write(master_fd)`, `ioctl(TIOCSWINSZ)` / `pty.Setsize`, `syscall.Kill`) are **strictly forbidden** while holding `PtyProcess.mu`. All OS syscalls execute 100% unlocked outside process locks. `PtyProcess.mu` is acquired exclusively for pure in-memory Go data structure operations (`xtermState.Resize()`, `xtermState.Clone()`, `xtermState.Write()`, buffer appends/flushes), strictly bounding lock windows ($< 5\text{ \mu s}$ for grid resizes and flushes, $< 50\text{ \mu s}$ for grid pointer cloning).
* **Lock-Free Async Snapshot Serialization**: Baseline state snapshots are generated by performing an $O(1)$ memory pointer clone of the `xterm-go` state engine under a microsecond lock ($< 50\text{ \mu s}$). Heavy string formatting, ANSI color encoding, and frame chunking ($32\text{ KB}$ / $64\text{ KB}$) execute 100% outside the process lock, ensuring zero stalls in the PTY read loop.
* **Domain-Driven Resync Execution**: Terminal resync transitions deterministically across three explicit operational modes: `ModeLive`, `ModePreSnapshot`, and `ModePostSnapshot`, ensuring zero data loss and zero state duplication during reconnection.
* **Deterministic Single-Writer Egress**: All outbound WebSocket frames pass through a single, lock-guarded FIFO write queue per connection (`wsConnection.WriteFrame`) to enforce strict sequential wire ordering across stdout data, status events, and resync markers.

## 2. System Architecture & Topology

The server architecture consists of three decoupled layers:

1. **Network Gateway**: Manages WebSocket connections (`/ws`), binary envelope framing/headers, and single-writer FIFO egress serialization.
2. **Workspace Controller**: Manages terminal process lifecycles, priority scheduling, and multi-terminal resync macro pipelines. It binds each PTY process's output callback directly to the Network Gateway egress queue.
3. **PTY Process (`PtyProcess`)**: Encapsulates the OS master file descriptor (`master_fd`) and `xterm-go` state engine. ### A. Network Gateway Layer

The gateway exposes a parameterless WebSocket endpoint at `/ws` for local developer sessions. It upgrades network connections directly into workspace bindings, enforces handshake rules, encapsulates binary protocol envelopes, and executes single-writer FIFO serialization for all outbound frames.

### B. Workspace Controller Layer

The workspace acts as the central domain controller for all active terminal objects in memory. It maps unique thirty-two-bit integer identifiers to their respective `PtyProcess` objects, manages priority-weighted execution queues, cleans up orphaned processes, and orchestrates multi-terminal resync macro workflows. It binds each `PtyProcess` output callback directly to the Network Gateway egress queue.

### C. Pseudo-Terminal Process Layer (`PtyProcess`)

Each running terminal process is encapsulated inside a `PtyProcess` object containing:

* **Master File Descriptor**: The Operating System PTY master file descriptor (`master_fd`) created during process spawning.
* **Process Handle**: The active Operating System child process reference.
* **Headless Terminal Engine**: The in-memory `xterm-go` state engine maintaining primary and alternate screen grids, color palettes, modes, and scrollback.
* **State Serializer**: The `xterm-go` serialization addon capable of generating a compact ANSI setup stream from the current state engine memory.
* **Terminal Read/Write Mutex**: A dedicated read/write lock (`PtyProcess.mu`) isolating background state updates from snapshot operations.
* **Resync Mode Indicator**: Tracks execution mode (`ModeLive`, `ModePreSnapshot`, `ModePostSnapshot`).
* **Transient Post-Snapshot Buffer (`postSnapshotBuffer`)**: A RAM buffer that stages stdout bytes produced during post-snapshot serialization.
* **Transport-Agnostic Output Callback**: An abstract function closure (`onOutput func([]byte)`) injected by the Workspace Controller to emit bytes without coupling `PtyProcess` to network protocols or WebSockets.

## 3. Concurrency, Execution Model & Kernel Invariants

### A. Continuous Non-Blocking Reader Loop

For each running process, a dedicated background reader loop continuously reads byte chunks from `master_fd` using Go's Netpoller (`O_NONBLOCK` combined with OS `epoll`):

1. **Passive VTE Update**: The chunk is passed into `xterm-go.Write()` under `PtyInstance.mu` ($< 5\text{ \mu s}$ lock window), continuously updating the in-memory character grid, cursor coordinates, and active modes regardless of network or resync state.
2. **Conditional Output Dispatch**: Depending on the active execution mode:
* **`ModeLive`**: The chunk is immediately dispatched to `onOutput` network egress.
* **`ModePreSnapshot`**: Live network dispatch is suppressed. Stdout bytes are absorbed directly into `xterm-go` memory for the upcoming baseline snapshot.
* **`ModePostSnapshot`**: The chunk is appended to `postSnapshotBuffer` AND absorbed into `xterm-go`. Live network dispatch remains suppressed.

If the reader encounters an end-of-file or input/output error, it drains remaining stdout bytes into `xterm-go`, updates the lifecycle state to exited, and dispatches the process exit event.

### B. Operating System & Memory Invariants

1. **Non-Blocking Kernel Read Invariant**: The Linux kernel allocates a $64\text{ KB}$ ring buffer for each PTY pair. `read(master_fd)` **must never be paused, delayed, or throttled**. Maintaining active reads prevents kernel buffer saturation and eliminates child process write-blocking deadlocks.
2. **Zero-Syscall Lock Bounding**: Operating System syscalls (`pty.Setsize`, `read`, `write`, `kill`) execute 100% unlocked outside `PtyInstance.mu`. `PtyInstance.mu` acquisitions are strictly limited to $O(1)$ memory pointer operations, integer mode swaps, state grid pointer cloning ($< 50\text{ \mu s}$), in-memory grid buffer resizes (`xtermState.Resize()`, $< 5\text{ \mu s}$), and RAM buffer appends ($< 5\text{ \mu s}$). Network I/O, WebSocket writes, string formatting, and socket flushing are strictly forbidden while holding this lock.
3. **Transient Memory Ceiling**: `postSnapshotBuffer` enforces a safety capacity limit ($2\text{ MB}$). If an extreme stdout flood occurs during resync, excess bytes update `xterm-go` memory but are truncated from `postSnapshotBuffer`, ensuring zero system out-of-memory crashes while maintaining $100\%$ screen grid accuracy.

## 4. Network Transport & Binary Wire Protocol

### A. Connection Endpoint

The server provides a clean WebSocket endpoint at `/ws` that requires no URL query parameters, upgrading directly into the single developer workspace.

### B. Binary Wire Envelope Layout

Every WebSocket frame transmitted over the wire follows a standardized binary framing layout consisting of three continuous sections:

1. **Opcode Header**: A two-byte big-endian unsigned integer representing the protocol command or event action (Bytes 0–1).
2. **Terminal Identifier**: A four-byte big-endian unsigned integer identifying the target terminal instance (Bytes 2–5).
3. **Payload**: A variable-length byte array containing raw terminal stream bytes or structured JSON objects depending on the opcode (Bytes 6+).

## 6. API Semantics & Operational Invariants

### A. Atomic State Substitution & Client Hydration

Resync follows strict atomic state substitution semantics on the client:

1. Upon receiving `ResyncPtyStartEvent` (`0x000c`), the client reads the target grid dimensions (`cols`, `rows`), executes `xterm.reset()` to wipe old state, and locks keyboard/UI input.
2. The server transmits the serialized baseline state snapshot as a sequence of $32\text{ KB}$ or $64\text{ KB}$ `PtyOutputEvent` (`0x0008`) chunks.
3. The client feeds these chunks sequentially into `xterm.write()`, restoring screen grid layout, colors, scrollback, and cursor position without freezing the main browser thread.
4. Upon receiving `ResyncPtyCompleteEvent` (`0x000d`), the client unlocks user input.
5. Any trailing `PtyOutputEvent` (`0x0008`) gap bytes (`postSnapshotBuffer`) immediately follow `ResyncPtyCompleteEvent` on the wire and are applied seamlessly to the restored grid.

### B. Pre-Resync Command Gating

Upon connection upgrade, the network gateway marks the WebSocket session as unsynced. Any operational command frames (`0x0001`, `0x0003`, `0x0007`) received **before** `ResyncWorkspaceCommand` (`0x000e`) are dropped to enforce correct handshake sequencing.

### C. Live Spawn Status Precedence

On live PTY creation (`SpawnPtyCommand` `0x0001`), the server must enqueue `SpawnPtyStatusEvent` (`0x0002`, `[0x00]`) to network egress **before** launching the background reader loop or emitting any `PtyOutputEvent` (`0x0008`) bytes for that terminal.

### D. Exit Frame Ordering

`PtyExitEvent` (`0x0005`) must **never** be emitted until the master file descriptor reaches end-of-file, all remaining stdout bytes have been processed by `xterm-go`, and all queued snapshot or `postSnapshotBuffer` output frames have flushed to egress.

### E. Instant Batch Destruction (`RemovePtyCommand` `0x0006`)

`RemovePtyCommand` operates as a non-blocking command accepting one or many terminal identifiers in a JSON array. For each target ID, the server sets an atomic `isDestroyed` flag, cancels any associated hydration `context.Context`, closes file descriptors, terminates child process groups, and removes `PtyInstance` objects from workspace memory immediately.

## 6. Workspace Macro Pipeline & Lifecycle Management

### A. Lifecycle State Machine

The Workspace Controller manages the high-level operational lifecycle for every terminal process in memory (`PtyStatus__Spawning`, `PtyStatus__Running`, `PtyStatus__Exited`).

### B. Spawn Execution Pipeline (`SpawnPtyCommand`)

1. **Client Request**: Client transmits `SpawnPtyCommand` (`0x0001`).
2. **Initial Event Emission**: Workspace Controller allocates a unique terminal ID and emits `SpawnPtyStatusEvent` (`0x0002`, status Spawning).
3. **Process Creation**: Spawns process via `pty.Start()`, constructs `PtyProcess` with `xtermState`, and binds `onOutput` callback to egress queue.
4. **Completion Event**: Emits `SpawnPtyStatusEvent` (`0x0002`, status Success, containing `pid`).

### C. Teardown & Removal (`RemovePtyCommand`)

1. **Client Request**: Client transmits `RemovePtyCommand` (`0x0006`).
2. **Resource Cleanup**: Workspace Controller cancels context, invokes `PtyProcess.Terminate(SIGKILL)` if process is running, closes `master_fd`, and removes instance reference from workspace memory.

## 7. Terminal Resync Architecture & Staging Rules

When a client transmits `ResyncWorkspaceCommand` (`0x000e`), the Workspace Controller orchestrates state recovery across three deterministic temporal boundaries for each terminal process: initiation ($w_0$), snapshot capture ($t_{\text{snap}}$), and handoff completion ($t_{\text{end}}$).

### A. Boundary $w_0$: Initiation & Pre-Snapshot Subsumption

The `PtyProcess` enters `ModePreSnapshot` automatically on socket disconnection or when the Workspace Controller processes `ResyncWorkspaceCommand` at microsecond $w_0$ via `TransitionFromLiveToPreSnapshot()`.

1. **Atomic Mode Mutation**: The process sets its mode to `ModePreSnapshot` and unbinds network output callbacks.
2. **Execution Behavior ($w_0 \to t_{\text{snap}}$)**: The background reader loop continues reading `master_fd` in a 100% unlocked path. Every byte read is processed directly by `xterm-go.Write()`, updating the grid live in memory. Network output dispatch is suppressed based on the operational mode.
3. **Subsumption Principle**: Bytes read between $w_0$ and $t_{\text{snap}}$ do not require buffering or network dispatch. Because `xterm-go` processes them live in memory, they are automatically incorporated into the baseline snapshot generated at $t_{\text{snap}}$.

### B. Boundary $t_{\text{snap}}$: Baseline Snapshot Capture & Lock-Free Serialization

When the Workspace Controller is ready to serialize state for terminal $T$, it invokes `TransitionFromPreToPostSnapshot()` on `PtyProcess` at microsecond $t_{\text{snap}}$.

1. **Grid Pointer Cloning**: Under a microsecond lock, the process executes an $O(1)$ memory pointer clone of internal `xterm-go` grid structures (`p.stateClone = p.xtermState.Clone()`, $< 50\text{ \mu s}$).
2. **Atomic Mode Mutation & Localized Reset**: Within the exact same microsecond lock window, the process transitions to `ModePostSnapshot` and executes a single localized buffer reset (`postSnapshotBuffer.Reset()`).
3. **Lock-Free Async Serialization**: Lock is released immediately ($< 50\text{ \mu s}$). Outside the lock, the Workspace Controller invokes `Serialize()` on `p.stateClone` to generate the baseline stream $H_T$. Heavy string formatting, ANSI encoding, and chunking execute completely outside process locks, guaranteeing zero stalls in the PTY reader loop.
4. **Execution Behavior ($t_{\text{snap}} \to t_{\text{end}}$)**: While $H_T$ is serializing asynchronously on the controller thread, the background reader loop continues reading `master_fd` in an unlocked path. Every byte read is processed by the primary `xterm-go.Write()` AND appended to `postSnapshotBuffer`.

### C. Boundary $t_{\text{end}}$: Atomic Handoff & Return to Live Streaming

Once the Workspace Controller finishes submitting all $H_T$ snapshot chunks to network egress, it emits `ResyncPtyCompleteEvent` (`0x000d`) and calls `TransitionFromPostToLiveMode()` on `PtyProcess` at microsecond $t_{\text{end}}$.

1. **Atomic Flush & Mutation**: Under a single microsecond lock acquisition ($< 5\text{ \mu s}$), the process executes two operations:
* It checks `postSnapshotBuffer`. If bytes accumulated during $t_{\text{snap}} \to t_{\text{end}}$, it invokes `p.onOutput(p.postSnapshotBuffer.Bytes())`, pushing the gap bytes into the connection's egress channel ahead of any live data.
* It transitions to `ModeLive`.
2. **Zero-Gap & Strict Order Guarantee**: Because calling `onOutput(postSnapshotBuffer)` and transitioning to `ModeLive` occur inside the same single microsecond lock acquisition, the background reader loop cannot execute a `ModeLive` read until `postSnapshotBuffer` is safely sitting in the egress queue. Live streaming stdout is guaranteed to land on the wire behind `postSnapshotBuffer`.

### D. Deterministic Wire Sequence

All frames pass through the connection's Single-Writer FIFO Egress Queue, guaranteeing exact chronological arrival at the browser:

$$\text{Wire Delivery Sequence: } [\text{ResyncPtyStartEvent}] \longrightarrow [\text{Snapshot } H_T \text{ Chunks}] \longrightarrow [\text{ResyncPtyCompleteEvent}] \longrightarrow [\text{postSnapshotBuffer}] \longrightarrow [\text{Live Output}]$$

### E. Mid-Resync Control-Plane Routing Policy

| Client Command | Mid-Resync Handling Policy |
| --- | --- |
| **`0x000e` `ResyncWorkspaceCommand**` | **Preempt & Restart**: Instantly cancel active resync `context.Context`, reset target PTY modes to `ModeLive`, and launch new resync pass. |
| **`0x0006` `RemovePtyCommand**` | **Immediate Teardown**: Set `isDestroyed = true`, cancel hydration `context.Context`, terminate child process, and purge RAM. Emits `ResyncPtyFailedEvent` (`0x000f`) if `ResyncPtyStartEvent` was already sent. |
| **`0x0004` `TerminatePtyCommand**` | **Signal Dispatch**: Dispatch OS signal (`syscall.Kill`) to process group immediately. `readLoop` catches `EOF`, drains into `xterm-go`/`postSnapshotBuffer`, and defers `PtyExitEvent` (`0x0005`) until after `TransitionFromPostToLiveMode()`. |
| **`0x0003` `ResizePtyCommand**` | **Intercept & Apply**: Call `pty.Setsize()` and update `xterm-go` grid under `PtyInstance.mu`. If in `ModePreSnapshot`, $H_T$ is serialized at new dimensions. If in `ModePostSnapshot`, process redraw bytes accumulate in `postSnapshotBuffer`. |
| **`0x0007` `WritePtyInputCommand**` | **Direct Write**: Send stdin directly to `master_fd` without blocking or server-side buffering. Response stdout lands in $H_T$ (if $w_0 \to t_{\text{snap}}$), `postSnapshotBuffer` (if $t_{\text{snap}} \to t_{\text{end}}$), or live output. |
| **`0x0009` `SetPtyPrioritiesCommand**` | **Scheduler Update**: Re-sort remaining unhydrated terminal queue in workspace memory or update egress scheduler weights for active frame dispatch. |

## 8. Operating System Integration & Signal Management

### A. PTY Process Creation (`creack/pty`)

Child processes are launched using `creack/pty.StartWithOptions`. The library handles slave PTY allocation, session leader creation (`setsid`), controlling terminal assignment (`TIOCSCTTY`), file descriptor duplication onto standard input, output, and error streams, and initial window size configuration.

### B. Native Kernel Window Resizing

When a `ResizePtyCommand` (`0x0003`) frame arrives, the server calls `pty.Setsize()` on `master_fd` and resizes the `xterm-go` grid in memory. Updating `master_fd` causes the Linux kernel to generate and dispatch a `SIGWINCH` signal directly to the slave process group.

### C. Process Group Termination

When a `TerminatePtyCommand` (`0x0004`) frame arrives, the server resolves the child process group identifier and sends the specified signal directly to the negative process group ID (`-pgid`), ensuring that sub-processes and shell pipelines terminate cleanly.

## 9. Resilience & Edge-Case Guarantees

* **High-Volume Output Floods**: High-volume log floods flow directly from the reader loop to network egress in `ModeLive`. During resync, floods update `xterm-go` live while `postSnapshotBuffer` captures post-$t_{\text{snap}}$ bytes up to its $10\text{ MB}$ capacity ceiling.
* **Rapid Client Reconnections**: Repeated connection drops and immediate reconnects cancel in-flight resync routines cleanly via Go `context.Context` cancellation without resource leaks, starting new hydration passes atomically.
* **Unrecognized Terminal ID in Resync**: Requesting resync for an identifier that failed creation or was dropped triggers `ResyncPtyStartEvent` (`0x000c`) followed immediately by `ResyncPtyFailedEvent` (`0x000f`), skipping history generation without stalling hydration for valid terminals.
* **Spawning Terminals During Resync**: If resync targets a terminal whose process creation is in progress, the server emits `ResyncPtyStartEvent` (`0x000c`) followed by `SpawnPtyStatusEvent` (`0x0002`, `[0x02]` Spawning), withholding `ResyncPtyCompleteEvent` (`0x000d`). When process creation completes, the server emits `SpawnPtyStatusEvent` (`0x0002`, `[0x00]` Success) followed by `ResyncPtyCompleteEvent`.
* **Child Process Exit Mid-Resync**: If a process exits during resync, the reader loop drains remaining stdout into `xterm-go` (and `postSnapshotBuffer` if post-$t_{\text{snap}}$), marks the instance as exited, and defers `PtyExitEvent` (`0x0005`) until after `CompleteResyncAndFlush()` flushes `postSnapshotBuffer`.
